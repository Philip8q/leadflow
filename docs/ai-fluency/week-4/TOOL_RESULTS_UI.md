Brief: https://internship.flyrank.ai/intern/assignments/FE-07

## Overview

Extends the [FE-06 streaming chat](./STREAMING_CHAT.md) with a server-side
tool: once the assistant has learned enough about a visitor, it calls
`scoreLead`, and the UI renders a real lead-score card instead of a JSON
dump. Per FlyRank's own Q&A guidance on FE-07 ("My suggestion would be to
use FE-06 and just continue building"), this builds on the same chat
rather than a separate app.

**Try it live:** https://leadflow-ten-sage.vercel.app/demo/lead-chat — hold
a normal conversation (intent, timeline, budget, contact method, property)
and the score card appears once the assistant has enough to work with.

## The tool: `scoreLead`

| | |
| --- | --- |
| **File** | [`lib/ai/lead-chat-tools.js`](../../../lib/ai/lead-chat-tools.js) |
| **Input schema** | `{ intent: "buy" \| "sell" \| "rent", timeline: "immediate" \| "weeks" \| "months" \| "browsing", budgetKnown: boolean, contactMethod: "phone" \| "email" \| "whatsapp" \| "none", propertyType: string }` |
| **Return shape** | `{ score: number (0-100), tier: "Hot" \| "Warm" \| "Cold", breakdown: Array<{ label, points, max, detail }>, summary: string }` |

The schema is deliberately small (per the brief's mentor tip: "every field
you add is a field the model can hallucinate"). The model's only job is to
classify what it already heard into these five fields — **the score itself
is never generated by the model.** `execute()` computes it with a plain,
deterministic point formula (timeline urgency + budget known + contact
method + property specifics), so the number in the card is always
reproducible from its inputs, never an LLM guess.

**Real error path, not a simulated one:** if `execute()` receives input
with essentially no qualifying signal at all, it throws instead of
returning a fabricated "Cold" score. That's the one non-obvious design
call here — a fully "Cold" tier is meaningful data (the visitor engaged
but volunteered nothing usable), whereas the tool being called with
nothing at all almost always means the model reached for it too early. The
UI needs to tell those two situations apart, so they take different tool
states.

## The four tool states

`app/demo/lead-chat/page.jsx` renders `<LeadScoreTool part={part} />`
(in [`components/LeadScoreCard.jsx`](../../../components/LeadScoreCard.jsx))
for every `tool-scoreLead` part in a message, switching on `part.state` —
the same state field the AI SDK's `useChat` already exposes, not a custom
state machine layered on top.

| State | What it answers | Visual treatment |
| --- | --- | --- |
| `input-streaming` | What is it doing? | A pulsing skeleton card — no numbers yet, because there aren't any |
| `input-available` | With what input? | A spinner + the fields the model has settled on so far, as small tags |
| `output-available` | What came back? | The real score card: tier badge, big score number, a progress bar per scoring factor |
| `output-error` | What went wrong? | A warning-toned card with the actual (safe) error message, styled nothing like the success card |

Each state is a visually distinct component, not the same card re-labeled —
`input-streaming` has no score-shaped layout at all (nothing to show yet),
`input-available` shows the *inputs* prominently since that's the only
real information available mid-call, and only `output-available` earns the
tier badge and progress bars. The transition from `input-available` to
`output-available` is a straight React re-render on the same message part
(same `toolCallId` key), so it swaps in place rather than jumping the
layout.

## Verification

- `npx eslint .` — clean
- `npx vitest run` — 15/15 (repo-wide suite, unaffected by this feature)
- `npm run build` — clean production build
- Directly unit-tested `scoreLead.execute()` in isolation: confirmed the
  scoring formula on a normal input, and confirmed the empty-input case
  throws exactly as designed
- Ran a real end-to-end conversation against the local dev server's
  `/api/chat` (raw HTTP, not just the UI): the model correctly extracted
  `{ intent: "sell", timeline: "immediate", budgetKnown: true,
  contactMethod: "whatsapp", propertyType: "3-bedroom house in Karen" }`
  from natural conversation, the tool returned a real `score: 100, tier:
  "Hot"`, and the assistant's follow-up text referenced the result without
  repeating the raw number — the full two-model-call round trip (extract →
  tool → close out) completed in ~6.8 seconds
